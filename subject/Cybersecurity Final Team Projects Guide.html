General guidelines for all teams

Purpose and minimum scope

Build a small functional Python application, demonstrate one assigned vulnerability in an isolated environment, implement a secured version, and provide repeatable tests. A command-line interface or small Flask application is sufficient; a polished UI is not required.

Use only local or isolated test systems and fictional accounts, files, payment records, and other data.

Submit both vulnerable and secured implementations, source code, setup instructions, and test evidence.

All team members must understand the code and describe their contributions.

AI coding assistance is permitted, but teams must verify and explain all submitted code.

Assignments

Three-week schedule

Weekly progress report format

Team, project, members, date, and reporting week

Objective and work completed (specific functions/files)

Screenshots, relevant code snippets, and test outputs

Difficulties, remaining risks, and next-week tasks

Individual contributions and a short progress summary

Suggested length: 2–4 pages per weekly report, excluding code attachments. Reports must show actual progress rather than theory alone.

Presentation: 2–10 December

Every team member should contribute. Present the same test against the vulnerable and secured versions, with a clear explanation of why the result changed.

Final report and feedback revision

Recommended report length: 8–12 pages excluding appendices. Include introduction, requirements, architecture, vulnerability analysis, vulnerable code, attack simulation, security design, tests and results, limitations, conclusion, references, and individual contributions.

Between 7 and 14 December, revise the implementation and report using instructor feedback. Include a section titled “Presentation Feedback and Implemented Improvements” with feedback, change made, and evidence of retesting.

Final submission — 14 December 2026

Three weekly progress reports

Final presentation slides

Vulnerable and secured source-code folders

Test scripts, synthetic sample data, and results

README with environment setup and execution steps

Final revised technical report including feedback-response table

Submit all required files through CTL. Do not include real credentials, private records, or production secrets.

01University Internship Document Portal
Team 2 · Broken object-level authorization (IDOR)

Project objective

Build a small local demonstration of university internship document portal. Identify and reproduce the main security issue (IDOR / broken object-level authorization), then implement and test appropriate defenses. Use only fictional data and isolated services.

Suggested technology and deliverables

Python 3, Flask (optional), SQLite, standard-library unittest or pytest, VS Code. Keep the interface simple. Submit vulnerable and secure versions, sample data, automated or repeatable tests, three weekly reports, slides, and a final revised report.

Week 1 — Prototype

9–15 November

1. Create Student A, Student B, and Coordinator test accounts.

2. Create fictional documents with document IDs and owner IDs.

3. Build login, document listing, upload, and download functions.

4. Create an intentionally vulnerable document retrieval route without ownership checks.

Weekly submission: Report 1 (15 November): requirements, role/data design, architecture, initial code, screenshots, issues.

Week 2 — Vulnerability and defense

16–22 November

1. As Student A, request Student B’s document by changing its identifier.

2. Record the response and explain why login alone is insufficient.

3. Check ownership or authorized coordinator role on every read, update, and delete.

4. Repeat the request and verify access is denied.

Weekly submission: Report 2 (22 November): vulnerability cause, controlled steps, observed outputs, defense code, initial retest.

Week 3 — Verification and presentation

23–30 November

1. Finish and clean up the secured implementation.

2. Run every required test and capture expected versus actual outcomes.

3. Document limitations and confirm normal functionality still works.

4. Prepare a 10-minute technical presentation and draft final report.

Weekly submission: Report 3 (30 November): final implementation, test table, screenshots, limitations, contributions.

Minimum security test checklist

Own document downloads successfully

Other student document is denied

Unauthorized update/delete is denied

Unauthenticated access is denied

Authorized coordinator access succeeds

Required demonstration

Show the same cross-student request in vulnerable and secured versions.

Presentation and final revision

Present between 30 November and 7 December: 10 minutes presentation/demo and 5 minutes Q&A. Explain the scenario, architecture, vulnerability, attack evidence, defenses, test comparison, and limitations.

From 10 to 14 December, incorporate instructor feedback into the application and final report. Add a feedback → modification → retest evidence table. Submit the complete revised technical report and source code by 14 December 2026.
